# Нагрузочные тесты

Код здесь не входит в сервер: `bench/loadgen` — отдельный Mix-проект без зависимостей. Его можно запускать на машинах-генераторах без кода сервера и без базы. `bench/seed.exs` — скрипт заливки, он выполняется внутри приложения mailstore.

## Сценарий idle

Открыть N сессий с заданной скоростью. Каждая делает LOGIN, SELECT и IDLE, затем висит. На один ящик приходится столько сессий, сколько папок в `--folders` (по умолчанию INBOX и Junk, то есть 2 соединения на ящик: многие клиенты держат отдельное соединение на каждую отслеживаемую папку).

```bash
# 1. Аккаунты user1..user5000@load.test с паролем pw и тремя письмами каждый
mix run bench/seed.exs -- --users 5000 --domain load.test --password pw --messages 3

# 2. Сервер как распределённая нода (loadgen читает её память через :erpc)
MAILSTORE_REPORT_MS=5000 elixir --sname mailstore --cookie loadtest --erl "+Q 131072" -S mix run --no-halt

# 3. Генератор (в другом терминале или на другой машине)
cd bench/loadgen
elixir --sname loadgen --cookie loadtest -S mix loadgen.idle \
  --sessions 10000 --users 5000 --rate 1000 --hold 25 --server-node mailstore@$(hostname -s)
```

Генератор печатает:
- время установки сессии (connect + LOGIN + SELECT + IDLE): p50, p95, p99;
- прирост памяти сервера на сессию сразу после разгона, по видам: processes, binary, ets, system;
- установившийся режим после hold: соединения к этому моменту ушли в гибернацию.

Полезные опции:
- `--until connect|login|select|idle` останавливает установку после указанного шага. Так можно найти шаг, на котором растёт память.
- `--source-ips 127.0.0.1,127.0.0.2` распределяет соединения по нескольким исходным IP.
- `--server-pid PID` меряет RSS и CPU процесса сервера через `ps` — так же для любого сервера.

Сервер со своей стороны пишет строку отчёта раз в `MAILSTORE_REPORT_MS`: число соединений, акторов, память, команд в секунду.

**Лимиты.** С одного исходного IP к одному порту сервера можно открыть ~16 тыс. соединений на macOS и ~28 тыс. на Linux. Для 100 тыс. нужны алиасы IP или несколько генераторов. Нужны также `ulimit -n` и `+Q` (лимит портов BEAM, по умолчанию 65536) на обеих сторонах.

Для экспериментов с памятью опции сокетов IMAP можно задать через окружение: `MAILSTORE_IMAP_SOCKET_OPTS="buffer=4096,recbuf=16384"`.

## Результаты (Mac mini, Postgres 17 в Docker, всё на одной машине)

| Прогон | Память на сессию (установившийся режим) | Из неё буфер сокета |
|---|---|---|
| исходно: `{active, :once}`, буфер Postgrex по умолчанию (~400 KB) | ~250 KB | ~240 KB |
| `{active, :once}`, буфер Postgrex 16 KB | 20,7 KB | 14,6 KB |
| **`{active, 100}`** (итог), буфер Postgrex 64 KB | **6,4 KB** | ~0 |
| `{active, 100}`, буфер Postgrex по умолчанию | 5,9 KB | ~0 |

Итог на 10 000 сессий: ошибок 0, установка p50 = 28 мс, p99 = 57 мс. Весь сервер (10 000 сессий и 5 000 акторов) занимает 118 MB. Из 6,4 KB процесс соединения после гибернации занимает 2,1 KB, остальное — доля акторов аккаунтов.

### Найденная проблема: простаивающий сокет держал чужой буфер чтения

Всё ниже проверено по исходникам OTP 29, `erts/emulator/drivers/common/inet_drv.c`.

1. **Перевзвод `{active, :once}` сразу занимает буфер.** `inet:setopts(S, [{active, once}])` вызывает в драйвере `tcp_recv(desc, 0)`: «try a read instead of just deliver». Если данных нет, `tcp_recv` уже взял буфер (`alloc_buffer(bufsz)`), получает `EWOULDBLOCK` и держит буфер, пока не придут данные. IMAP-соединение в IDLE ждёт до 30 минут, и всё это время буфер занят.
2. **Буфер берётся из кеша, любого подходящего размера.** У `alloc_buffer` есть кеш освобождённых буферов на поток-планировщик: до 14 штук и до 1 MB суммарно. Он отдаёт верхний буфер, если `size >= minsz`, без ограничения сверху. Поэтому `buffer: 4096` у IMAP-сокета ничего не менял.
3. **Откуда огромные буферы в кеше.** Postgrex выставляет своему сокету `buffer = max(buffer, sndbuf, recbuf)`, то есть ~400 KB при системных настройках. Каждый ответ базы читается в буфер такого размера, и после разбора буфер уходит в тот же кеш. Сессия делает запросы в БД в своём процессе и на том же планировщике, а затем перевзводит свой сокет и забирает из кеша бывший буфер Postgrex.

Как нашли: `--until` показал рост на шагах с запросами в БД; `+MBatags true` и `:instrument.allocations/1` показали, что это `drv_binary` драйвера `tcp_inet`, по одному блоку на сокет; голый `gen_tcp` с одним `Repo.query!` воспроизвёл эффект.

**Исправления:**
- `Imap.Connection` использует `{active, 100}` и перевзводит сокет по `{:tcp_passive, _}` раз в 100 сообщений. Доставив данные, драйвер освобождает буфер, и простаивающий сокет не держит его вовсе. Число 100 ограничивает очередь сообщений процесса, если клиент начнёт заваливать сервер.
- Буфер Postgrex ограничен 64 KB (`socket_options: [buffer: 65_536]`). Наши ответы весят единицы килобайт, а 400 KB на каждый ответ — лишние аллокации. Если `buffer` задан явно, Postgrex свою логику с `max()` не применяет.

Без исправлений 100 тыс. соединений заняли бы ~25 GB. С исправлениями — ~0,65 GB.

### Реальный размер папок (1 000 сессий, INBOX по 2 000 писем)

В прогонах выше ящики были почти пустыми. Здесь у каждого из 1 000 ящиков в INBOX по 2 000 писем: столько набирается примерно за 30 дней при ~60 входящих в сутки на ящик (срок хранения — допущение). Заливка — `bench/seed_folders.exs`, прямо в SQL. Одна сессия на ящик, то есть свой актор у каждой сессии.

```bash
MAILSTORE_IMAP_PORT=0 mix run bench/seed_folders.exs -- --users 1000 --domain big.test --fill 2000
cd bench/loadgen && elixir --sname loadgen --cookie loadtest -S mix loadgen.idle \
  --sessions 1000 --users 1000 --folders INBOX --user-format "big%d@big.test" --hold 20 \
  --server-node mailstore@$(hostname -s)
```

| Состояние INBOX | Диапазонов UID на папку | Процесс соединения | Всего на сессию (с актором) | Прежнее хранение добавило бы |
|---|---|---|---|---|
| 2 000 писем, без удалений | 1 | 2,1 KB | 9,6 KB | +16 KB |
| удалено ~1% | 21 | 2,6 KB | 9,7 KB | +16 KB |
| удалено ~10% | 179 | 6,3 KB | 14,1 KB | +10 KB |
| удалено каждое второе (худший случай, простой кортеж) | 901 | 9,1 KB | 16,5 KB | 0 |

- Установка сессии с SELECT большой папки: p50 = 27–29 мс, p99 ≤ 144 мс при разгоне 500 сессий в секунду. Диапазоны приходят из SQL одной строкой на диапазон.
- Процесс соединения растёт ровно на размер таблицы UID: ~24 байта на диапазон или 8 байт на письмо в худшем случае. Всё остальное от размера папки не зависит.
- «Всего на сессию» включает актор аккаунта (~2,4 KB). Здесь на каждую сессию свой актор; при двух сессиях на ящик на сессию придётся ~1,2 KB.

### Что это значит для памяти

С реальным размером папок: ~9–15 KB на сессию вместе с актором, в худшем случае ~17 KB. На 100 тыс. сессий это **~1–1,7 GB**. По памяти BEAM-нодам хватит небольшого объёма, упираться они будут в CPU на команды.

Оговорки:
- Без TLS: в целевой схеме его снимает HAProxy, и там своя память на соединение.
- Мерили на одной машине, клиент и сервер на loopback.
- Сценарий idle; профиль опроса — следующий сценарий.
- На macOS повторный прогон сразу после предыдущего может упереться в эфемерные порты клиента: закрытые соединения ~30 с висят в TIME_WAIT. Надо подождать или добавить `--source-ips`.

## Сценарий poller

N постоянных сессий. Каждая раз в `--interval` секунд выполняет цикл команд, как сервис, опрашивающий ящики. Одновременно сервер принимает новую почту со скоростью `--deliver-rate` писем в секунду: письма отправляются через `:erpc` в `Mailstore.Delivery`, тем же путём, каким будет работать консьюмер очереди входящих. После разгона и прогрева одного интервала мерится окно `--duration`:
- задержки по командам на стороне клиента;
- CPU сервера (`:erlang.statistics(:runtime)`) и CPU на команду;
- CPU Postgres из cgroup контейнера (`--pg-container`).

```bash
cd bench/loadgen
elixir --sname loadgen --cookie loadtest -S mix loadgen.poller \
  --sessions 5000 --users 5000 --interval 5 --duration 30 \
  --cycle noop,search_new,fetch_new,store_seen --deliver-rate 100 \
  --pg-container mailstore-pg --server-node mailstore@$(hostname -s)
```

Для серверов без `:erpc` (Stalwart) доставку задаёт `--deliver-lmtp HOST:PORT`, а CPU и память сервера — `--server-pid PID` (замер через `ps`; работает и для mailstore, им сравнивались серверы). Фактический темп доставок за окно замера печатается в отчёте.

Шаги цикла: `noop`, `status`, `select`, `search_unseen`, `search_new` (`UID SEARCH UID <last+1>:*`), `fetch_new` (`BODY.PEEK[]` новых писем), `store_seen`, `fetch_flags` (`UID FETCH 1:* FLAGS`). Опция `--reconnect-mean` добавляет переподключения, как у реальных клиентов (~30 мин).

**Профиль команд реальных клиентов неизвестен,** поэтому ниже цена каждой команды отдельно, а не один «реалистичный» прогон.

### Результаты (5 000 сессий, сервер запущен с `+sbwt none +sbwtdcpu none +sbwtdio none`)

Цена команды — приращение CPU на одну дополнительную команду. Её считали по двум прогонам с частотой опроса 1 000 и 5 000 команд в секунду, чтобы исключить фоновое потребление VM.

| Команда | CPU сервера на команду | CPU Postgres на команду | Задержка на клиенте p50 / p99 (1 000 команд/с) |
|---|---|---|---|
| NOOP | ~30 мкс | 0 | 0,2 / 2,9 мс |
| STATUS (из памяти актора) | ~50 мкс | ~0 | 0,3 / 2,9 мс |
| UID SEARCH UID n:* | ~70 мкс | ~90 мкс | 1,4 / 11,6 мс |
| SELECT INBOX повторно | ~190 мкс | ~370 мкс | 1,4 / 32,8 мс |
| Доставка письма | ~0,5 мс | ~1 мс | — |

Типичный цикл (NOOP, SEARCH новых, FETCH новых, STORE \Seen) раз в 5 с плюс 100 доставок в секунду: 2 200 команд/с, сервер 0,24 ядра, Postgres 0,38 ядра. Задержки p99: NOOP 1,4 мс, SEARCH 2,9 мс, FETCH 4,1 мс, STORE 11,6 мс.

### Что видно

- **Протокольный слой дешёвый:** ~30 мкс CPU на раунд команды. Дорого то, что ходит в БД.
- **`UID SEARCH UID n:*` — главный запрос поллера — ходит в базу зря.** Сейчас SEARCH загружает метаданные всех писем папки (вместе с envelope) и фильтрует в памяти. На поиск только по номерам или UID можно ответить из таблицы UID сессии, вообще без БД; UNSEEN — по частичному индексу. При 5 000 поисков в секунду пул БД из 20 соединений уже не успевает: p99 = 262 мс, Postgres 0,75 ядра.
- **SELECT дорогой:** каждый раз грузит список UID и непрочитанные. Если клиенты переоткрывают папку на каждом опросе, список UID горячих папок стоит держать в памяти актора.
- **Доставка:** одна транзакция на письмо. 1 000 писем/с — это ~0,5 ядра сервера и ~1 ядро Postgres. Group commit в акторе уменьшит долю Postgres.
- **Busy-wait планировщиков BEAM** при малой нагрузке завышает потребление CPU, поэтому для замеров его отключали. На общих машинах это разумная настройка и в эксплуатации.

### После быстрых путей SEARCH и UidMap на диапазонах

Те же 5 000 сессий, тот же сервер:

| Профиль | Было | Стало |
|---|---|---|
| `UID SEARCH UID n:*`, 5 000/с | сервер 0,48 ядра, Postgres 0,75, p99 262 мс | **сервер 0,19 ядра (как NOOP), Postgres 0,01, p99 8,2 мс** |
| `UID SEARCH UNSEEN`, 5 000/с | — | сервер 0,38, Postgres 0,66, p99 11,6 мс (один запрос по частичному индексу) |
| повторный SELECT, 1 000/с | сервер 0,22, Postgres 0,37, p99 32,8 мс | сервер 0,22, Postgres 0,39, p99 8,2 мс |

- Поиск по UID и номерам отвечает из таблицы UID сессии и в базу не ходит.
- UNSEEN — один запрос по частичному индексу.
- Поиск по флагам, размеру и датам читает узкие строки без envelope.
- Перед поиском сессия применяет накопившиеся уведомления: новое письмо попадает в результат, а `EXISTS` уходит клиенту раньше.
- У SELECT упала задержка, но не CPU. Папки в тесте маленькие, и цена здесь в самих запросах (два запроса и вызов актора), а не в объёме данных. Убрать их можно, держа состояние горячих папок в акторе.
- Память `UidMap` на папку из 2 000 писем: 192 байта без дыр, 672 байта с 20 дырами, 16 KB в худшем случае (удалено каждое второе письмо; тогда используется простой кортеж). Раньше всегда было 16 KB.

## TLS через HAProxy

`bench/loadgen` умеет `--tls` и ходит на HAProxy (`localhost:10993`). HAProxy снимает TLS и передаёт открытый трафик на `proxy_port` BEAM с заголовком PROXY v2.

```bash
deploy/haproxy/gen-cert.sh && docker compose up -d haproxy
cd bench/loadgen && elixir --sname loadgen --cookie loadtest -S mix loadgen.idle --tls --port 10993 \
  --sessions 7000 --users 5000 --rate 700 --hold 30 --server-node mailstore@$(hostname -s)
# память и CPU HAProxy: docker exec mailstore-haproxy cat /sys/fs/cgroup/memory.current /sys/fs/cgroup/cpu.stat
```

Что измерено на Mac mini через Docker Desktop:
- **Работает end-to-end:** Python `imaplib.IMAP4_SSL` и генератор проходят TLS 1.3 (`TLS_AES_256_GCM_SHA384`); сервер видит настоящий IP клиента; health checks HAProxy (заголовок LOCAL) обрабатываются.
- **Память HAProxy — ~32–36 KB на простаивающее TLS-соединение**, стабильно в трёх прогонах на 2,5–7,8 тыс. соединений. На 100 тыс. соединений это ~3,4 GB, то есть больше, чем на стороне BEAM (~10–15 KB на сессию). Варианты: настройки HAProxy (`tune.bufsize`, `tune.ssl.*`) или TLS в самом BEAM (`:ssl`, его память ещё надо измерить).
- **CPU и задержку рукопожатий здесь измерить не удалось.** Проброс портов Docker Desktop занимает по два эфемерных порта хоста на сессию: при ~8 тыс. сессий получили `eaddrnotavail`, сброшенные соединения и p99 установки сессии до 10–19 с из-за повторов TCP. Нужен прогон на Linux с отдельными машинами. Сертификат по умолчанию — ECDSA P-256: подпись в рукопожатии стоит в разы меньше RSA-2048. В реальной установке стоит держать оба сертификата, ECDSA и RSA для старых клиентов.

## Сравнение со Stalwart

Stalwart v1.2.0 (Community, AGPL) против mailstore на тех же сценариях: Mac mini (10 ядер), оба сервера нативно, Postgres 17 в Docker общий (у Stalwart своя база), 5 000 ящиков по 3 письма, одинаковый пароль. Стенд и все отличия настроек Stalwart от стандартных — в [bench/stalwart/README.md](stalwart/README.md). Главное из настроек: у Stalwart выключены спам-фильтр и полнотекстовая индексация, потому что у mailstore их нет.

**Методика.** CPU и память обоих серверов меряются снаружи через `ps` (`--server-pid`). Для BEAM `ps` показывает в 1,8–2 раза больше CPU, чем `:erlang.statistics(:runtime)`, которым мерились цифры выше: в счёт идут dirty-планировщики, async- и IO-потоки. Поэтому NOOP здесь стоит 75 мкс, а не 30. Цена команды — приращение CPU между прогонами на 1 000 и 5 000 команд/с. Доставка в mailstore идёт через `:erpc` в `Mailstore.Delivery`, в Stalwart — по LMTP (4 соединения), то есть у Stalwart в цену входит ещё и разбор протокола.

### Простаивающие сессии (10 000 сессий: INBOX и папка спама у каждого из 5 000 ящиков)

| | mailstore | Stalwart |
|---|---|---|
| RSS на сессию после удержания | 12,9 KB (по учёту BEAM 6,6 KB) | **2,5 KB** |
| RSS на сессию сразу после разгона 1 000/с | 56,8 KB | 9,8 KB |
| Установка при 200/с, первый вход: p50 / p99 | 38 / 52 мс | 56 / 115 мс |
| Установка при 200/с, повторный вход: p50 / p99 | **9 / 16 мс** | 52 / 166 мс |
| CPU на первый LOGIN (хеш пароля) | ~34 мс (PBKDF2, 100 000 итераций) | ~25 мс (стандартный хеш Stalwart) |
| CPU на повторную сессию целиком | **0,84 мс** (кеш логинов) | 24,6 мс (кеша нет) |
| CPU на LOGIN с хешем SHA512-CRYPT из Dovecot | — (схема не реализована) | 1,2 мс |

Кеша логинов у Stalwart нет: каждый LOGIN заново проверяет хеш. Со стандартным хешем это ~25 мс CPU на вход, и разгон 1 000 сессий/с упирается в CPU (p50 установки 11 с против 3,5 с у mailstore). С хешами, импортированными из Dovecot (SHA512-CRYPT, 5 000 раундов), вход стоит 1,2 мс, и разница почти пропадает.

|---|---|---|---|
| NOOP | 75 / 0 мкс | **30 / 0 мкс** | 5,8 / 4,1 мс |
| SELECT INBOX повторно | 220 / 140 мкс | **28 / ~0 мкс** | 8,2 / 5,8 мс |
| UID SEARCH UNSEEN | 120 / 80 мкс | **34 / ~0 мкс** | 11,6 / 8,2 мс |
| Доставка письма | 0,89 / 0,75 мс | 0,55 / 1,07 мс | — |

| | mailstore | Stalwart |
|---|---|---|
| Команд в секунду | 2 207 | 2 154 |
| Доставок в секунду | 99 | 77 |
| CPU сервера (`ps`) | 0,34 ядра | **0,17 ядра** |
| CPU Postgres | 0,30 ядра | 0,27 ядра |
| p99: NOOP / SEARCH / FETCH / STORE | 2,0 / 0,7 / 5,8 / 8,2 мс | 2,0 / 0,3 / 2,0 / 2,9 мс |
| RSS сервера | 459 MB | 227 MB |

У Stalwart в этом прогоне на 22 доставки в секунду меньше: генератор не дотянул темп по LMTP. По цене доставки это ~0,04 ядра на обоих, на вывод не влияет.

### Что видно

- **Stalwart быстрее на всех замеренных командах.** Главное — SELECT и SEARCH UNSEEN: они почти не дороже NOOP, а Postgres при росте их частоты не нагружается. Состояние папок у Stalwart лежит в памяти. mailstore на каждый SELECT и UNSEEN ходил в базу; это перенято, см. «SELECT и UNSEEN из памяти актора» ниже.
- **Память на простаивающую сессию** у обоих мала: 2,5 и 12,9 KB. На 100 тыс. сессий это 250 MB против 1,3 GB, и то и другое приемлемо.
- **Доставка стоит одинаково**, ~1,6 мс CPU на письмо (сервер плюс Postgres) у обоих.
- **Протокольный слой mailstore дороже в 2,5 раза** (NOOP 75 против 30 мкс). При 97 тыс. соединений с типичным профилем это доли ядра, не решающая разница.
- **Решает не CPU, а модель хранения.** Её этот стенд не мерил, сравнение — ниже.

## SELECT и UNSEEN из памяти актора

Перенято у Stalwart: актор аккаунта держит для открытых папок все UID и непрочитанные (`Core.UidMap`, диапазонами) и обновляет их своими же записями. SELECT получает снимок вместе с подпиской, UNSEEN спрашивает актор. Та же матрица, что в сравнении со Stalwart (5 000 сессий, CPU через `ps`, цена — приращение между 1 000 и 5 000 команд/с):

| Команда | Было: сервер / Postgres | Стало: сервер / Postgres | Stalwart | p99 при 5 000/с: было / стало |
|---|---|---|---|---|
| SELECT INBOX повторно | 220 / 140 мкс | **99 / 0 мкс** | 28 / ~0 мкс | 8,2 / 5,8 мс |
| UID SEARCH UNSEEN | 120 / 80 мкс | **92 / 0 мкс** | 34 / ~0 мкс | 11,6 / 8,2 мс |
| NOOP (для сравнения) | 75 / 0 мкс | 75 / 0 мкс | 30 / 0 мкс | 5,8 / 5,8 мс |

- **Postgres больше не участвует:** при 5 000 SELECT или UNSEEN в секунду он стоит на нуле (было 1,04 и 0,65 ядра).
- **SELECT и UNSEEN теперь на 17–25 мкс дороже NOOP.** Оставшийся разрыв со Stalwart — это цена самого раунда команды в нашем протокольном слое (75 против 30 мкс), а не данных.
- **Память:** 7,2 KB на простаивающую сессию против 6,6 KB (10 000 сессий, 5 000 аккаунтов, по две открытые папки), то есть ~1,2 KB на аккаунт за состояние двух папок.
- **Типичный цикл** (NOOP, поиск новых, FETCH, STORE) не изменился: SELECT и UNSEEN в нём нет.

## Очередь входящих (Kafka)

`Mailstore.Ingest` читает топики `mailhub_relay_sender_in.basic` и `.priority` (формат записи — в `Ingest.Record`) и пишет пачками: одна транзакция на шард на пачку до 200 записей. Запись идемпотентна: ключ доставки (SHA-256 получателя и байтов письма) записывается в `deliveries` в той же транзакции, поэтому повтор ничего не пишет и не тратит UID. Офсеты коммитятся в Kafka раз в 5 с, а не после каждой пачки.

**Стенд** (`bench/ingest`): Kafka 4.1.1 в Docker (один узел, 16 партиций на топик), Postgres 17 в Docker, mailstore нативно, Mac mini. Генератор пишет записи в формате топика: письмо ~4 KB (Authentication-Results, DKIM, два Received, multipart/alternative), 70% warmup, 1% на несуществующие адреса, получатели — 5 000 ящиков. CPU узла меряется через `ps` (как в остальных замерах, в счёт идёт и холостая прокрутка планировщиков), CPU Postgres — по cgroup контейнера; оба делятся на число записанных писем.

### Разбор накопленной очереди (100 000 записей)

| Настройка | Записей/с | Записей в пачке | CPU узла на письмо | CPU Postgres на письмо |
|---|---|---|---|---|
| по умолчанию: окно 200 мс, 2 батчера | 6 589 | 199 | 204 мкс | 105 мкс |
| окно 50 мс, 4 батчера | 8 949 | 137 | 193 мкс | 79 мкс |
| транзакция на каждое письмо (`batch_size 1`) | 505 | 1 | 1 665 мкс | 800 мкс |
| для сравнения: доставка по одному через `:erpc` (сценарий poller) | — | — | 890 мкс | 750 мкс |

Пачки снижают CPU на письмо в 8 раз на узле и в 8–10 раз в Postgres. Транзакция занимает ~40 мс на 200 писем.

### Постоянный поток 1 000 записей/с (60 с)

| Настройка | Записей в пачке | CPU узла на письмо | CPU Postgres на письмо |
|---|---|---|---|
| пачки по партиции Kafka (как в BroadwayKafka по умолчанию), окно 50 мс, 4 батчера | 6,5 | 646 мкс | 281 мкс |
| пачки через все партиции, окно 50 мс, 4 батчера | 17 | 548 мкс | 309 мкс |
| пачки через все партиции, окно 200 мс, 2 батчера (по умолчанию) | 106 | 523 мкс | 193 мкс |
| то же без холостой прокрутки планировщиков (`+sbwt none`) | 107 | 439 мкс | 183 мкс |

Задержка с настройками по умолчанию — от записи в Kafka до коммита в Postgres, для самой старой записи пачки: p50 326 мс, p99 424 мс. Письмо, отправленное в Kafka, приходит в IDLE-сессию как `* N EXISTS` через 241 мс.

На узле при потоке письмо дороже, чем при разборе очереди: 0,44 мс против 0,2 мс. Причины:
- опрос пустых партиций (см. ниже) — это около 94 мкс на письмо при 1 000/с;
- выборка приносит по несколько записей, и накладные расходы на выборку и подтверждение делятся на меньшее число писем.

### Что пришлось настроить в BroadwayKafka

- **Опрос партиций по очереди.** Продюсер BroadwayKafka — один процесс, он делает синхронный fetch каждой назначенной партиции по очереди. На пустой партиции брокер держит запрос до `max_wait_time` (по умолчанию 1 с), а после круга продюсер ждёт `receive_interval` (2 с). При 32 партициях круг занимал больше 30 с, и пачки приходили ступеньками. Исправлено:
  - `max_wait_time` — 10 мс;
  - `receive_interval` — 50 мс;
  - 4 продюсера (4 члена группы, партиции делятся между ними).

  Цена: 0,09 ядра на узел вхолостую, без писем.
- **Пачки по партиции.** BroadwayKafka кладёт в одну пачку только записи одной партиции, чтобы сохранить порядок. Нам порядок не нужен: записи независимы, UID выдаёт база. Общий `batch_key` увеличил пачки при 1 000 записей/с с 6,5 до 106. Подтверждения при этом верны: офсеты, подтверждённые не по порядку, коммитятся, когда становятся непрерывными.
- **Коммит офсета на каждый ack.** По умолчанию BroadwayKafka коммитит офсет после каждой пачки (`offset_commit_on_ack`). С идемпотентной записью это не нужно: коммит раз в 5 с, повтор после падения опознаётся.

### Падения

- **`kill -9` посреди потока** (`bench/ingest/restart.sh`, 50 000 записей). Первый экземпляр успел записать 20 798 писем и погиб до первого коммита офсетов. Второй, с той же группой, перечитал все 50 000 записей:
  - 20 798 опознаны как дубли;
  - 28 739 записаны впервые;
  - итого в базе 49 537 писем — ровно число записей на существующие адреса;
  - дублей нет, дыр в UID нет ни в одной папке.
- **Перезапуск Postgres посреди потока** (3 000 записей/с). Пачка повторялась с нарастающей паузой (8 повторов), пока база не вернулась; в dead letter ничего не ушло. Итог 59 376 писем, ровно ожидаемое, без дублей.

### Цена правил доставки

Это 40 правил, перенесённых из продового sieve (локальный набор, в репозиторий не входит). Замер A/B на одной и той же базе, 50 000 записей, правила включены и выключены поочерёдно:

| | Записей/с | CPU узла на письмо | CPU Postgres на письмо |
|---|---|---|---|
| правила выключены (2 прогона) | 5 448–5 450 | 211–216 мкс | 144–158 мкс |
| правила включены (2 прогона) | 4 087–4 883 | 278 мкс | 197–281 мкс |

- **Узел.** Правила добавляют около 65 мкс CPU на письмо, это совпадает с микрозамером: ~57 мкс на обычное письмо, на котором выполняются все правила. Из них ~31 мкс приходится на проверки заголовков и ~28 мкс на проверки тела. Части письма раскодируются один раз, дерево MIME берётся то же, что для записи.
- **Postgres.** Правила его не трогают: разброс 144–281 мкс от прогона к прогону не зависит от того, включены ли правила. К этому моменту текущая недельная партиция `messages` выросла почти до миллиона строк, а `deliveries` — до ~900 тысяч, и первый прогон после этого дал 430 мкс в Postgres. Почему именно, не разбирал: `shared_buffers` здесь 512 MB, так что это не обязательно нехватка памяти.

### Как запустить

```bash
bench/ingest/kafka.sh start                     # Kafka на localhost:9092, топики по 16 партиций
mix run bench/seed.exs -- --users 5000 --messages 0
mix run --no-start bench/ingest/produce.exs -- --count 100000          # накопленная очередь
MAILSTORE_KAFKA_HOSTS=localhost:9092 MAILSTORE_KAFKA_GROUP=bench-1 MAILSTORE_KAFKA_OFFSET_RESET=earliest \
  MAILSTORE_IMAP_PORT=0 mix run bench/ingest/measure.exs -- --expect 100000 --pg-container mailstore-pg
mix run --no-start bench/ingest/produce.exs -- --count 60000 --rate 1000   # поток, параллельно с measure.exs
bench/ingest/restart.sh 50000                   # kill -9 посреди потока и проверка базы
bench/ingest/kafka.sh stop
```

`MAILSTORE_INGEST_BATCH_SIZE`, `MAILSTORE_INGEST_BATCH_TIMEOUT` и `MAILSTORE_INGEST_BATCHERS` меняют настройки пачек.
