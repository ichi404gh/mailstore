# mailstore — прототип хранилища почты на Elixir

Прототип IMAP-кластера: IMAP4rev1-сервер поверх слоя хранения и координации. Вычисления (BEAM-ноды без состояния) отделены от хранения (шарды Postgres), поэтому их можно масштабировать по отдельности, а ящики не привязаны к конкретному серверу.

Целевой профиль — сотни тысяч или миллион ящиков и десятки миллионов писем в сутки, в основном небольшие автоматические письма (warmup) и ответы; ящики опрашивают сервисы по IMAP, мастер-инбоксы открывают обычными почтовыми программами. Диаграммы архитектуры — в [docs/architecture.md](docs/architecture.md), все замеры — в [bench/README.md](bench/README.md).

## Статус (26.11.2026)

### Сделано

- **Хранилище.**
  - Справочник (tenants, домены, аккаунты, правила пересылки) и шард (папки, метаданные писем, тела, журнал удалений).
  - Политики хранения в конфиге (`Mailbox.Retention`): срок по политике, классы писем → политики; партиции по политике и неделе, удаление по расписанию без блокировки трафика (`DETACH CONCURRENTLY`). По умолчанию warmup 30 дней, остальное 365.
  - Актор аккаунта: выдаёт UID и MODSEQ, рассылает изменения сессиям.
- **Кластер BEAM-нод** (`Mailstore.Cluster`, `Mailbox.Placement`):
  - актор ящика работает на ноде-владельце. Её выбирает rendezvous-хеширование по `account_id` среди нод в группе `:pg`, поэтому при входе или уходе ноды переезжают только её ящики;
  - вызовы актора и уведомления о доставке с любой ноды идут на владельца через `:erpc`, актор шлёт EXISTS / FLAGS / EXPUNGE сессиям на любой ноде;
  - когда состав кластера меняется, нода останавливает акторы чужих ящиков, и их сессии переподписываются у нового владельца;
  - пока ноды по-разному видят состав кластера (миллисекунды), у ящика может быть два актора. Данные от этого не страдают, UID выдаёт база. Но сессии на старом акторе не получают изменений, прошедших через новый, и догоняют их при переподписке. Дублей нет: события применяются идемпотентно;
  - проверено на настоящих нодах: клиент в IDLE на одной ноде получает письмо, записанное через другую, и переживает `kill -9` ноды-владельца без переподключения.
- **Шарды по tenant** (`Mailstore.Shards`):
  - реестр `shards` и `tenants.shard` лежат в справочнике, на нодах — кеш «tenant → шард» и свой Ecto-репозиторий на каждый шард, создаваемый во время работы, поэтому код записи и чтения не изменился;
  - шард добавляется на ходу, без перезапуска: `Shards.register/3` записывает его в реестр, проверяет, что схема базы не отстаёт, выдаёт свой диапазон `folders.id` (id папок не пересекаются между шардами) и рассылает кластеру; ноды открывают пул сразу, а пропустившая рассылку нода — при сверке раз в 30 с;
  - справочник и шарды — разные базы со своими схемами: `priv/repo/migrations` для справочника, `priv/shard/migrations` для шарда. В разработке это базы одного сервера Postgres: `mailstore_dev` для справочника и `mailstore_dev_shard1` для почты;
  - базу шарда создаёт эксплуатация, приложение только подключается. `mix mailstore.migrate` мигрирует справочник, регистрирует начальный шард из конфигурации (`:bootstrap_shards`) и мигрирует все шарды; её и запускать при деплое вместо `mix ecto.migrate`. `create:` и `migrate:` в `register` нужны для разработки и тестов;
  - `Shards.move_tenant/2` переносит tenant без простоя: копирование без блокировок, затем заморозка на миллисекунды (строки папок блокируются, докопируется дельта по MODSEQ и журналу удалений, папки на старом шарде помечаются `fenced`), затем переключение в справочнике; записи, упёршиеся в пометку, повторяются на новом шарде;
  - в тесте перенос шёл, пока параллельно доставлялись письма и менялись флаги: ни одно письмо не потерялось и не задвоилось, заморозка длилась 13–16 мс;
  - удаление по сроку и поддержка партиций работают на всех шардах.
  - Доставка с копией в мастер-инбокс, redirect и внешней пересылкой.
- **Приём из Kafka** (`Mailstore.Ingest`, топики входящих, по умолчанию `mailstore.inbound` и `mailstore.inbound.priority`; итоги в [bench/README.md](bench/README.md#очередь-входящих-kafka)):
  - Broadway: процессоры параллельно разбирают JSON, MIME и сжимают тело, пачка до 200 записей пишется одной транзакцией на шард;
  - идемпотентная запись: ключ доставки (хеш получателя и байтов) в `deliveries` в той же транзакции, повтор ничего не пишет и не тратит UID, поэтому офсеты коммитятся раз в 5 с;
  - CPU на письмо: 0,2 мс узла + 0,1 мс Postgres при разборе очереди (было 0,9 + 0,75 мс), 6 600 писем/с на одной ноде; при потоке 1 000/с — 0,44 + 0,18 мс, задержка от Kafka до коммита ~0,3 с;
  - `kill -9` посреди потока и перезапуск Postgres: всё записано ровно один раз, дыр в UID нет;
  - нечитаемая запись уходит в dead-letter топик, недоступная база не пропускает письма: пачка ждёт с паузами, пока база не вернётся.
- **Правила доставки вместо sieve** (`Core.Rules`, данные в `delivery_rules`; см. «Правила доставки» ниже):
  - условия и действия хранятся данными (JSON), а не в шаблоне; правила бывают общими, на tenant и на ящик, меняются без перезапуска;
  - правила существующего sieve-скрипта переносятся в этот формат один в один; реальный набор хранится вне репозитория, формат показан в `priv/delivery_rules/example.json`;
  - около 60 мкс CPU на письмо, если выполняются все правила.
- **IMAP4rev1-сервер.**
  - Команды: LOGIN, LIST/LSUB, STATUS, SELECT/EXAMINE, CREATE/DELETE/RENAME, SUBSCRIBE/UNSUBSCRIBE, APPEND, FETCH, STORE, SEARCH, COPY/MOVE, EXPUNGE, IDLE (и UID-варианты), UIDPLUS.
  - Уведомления об изменениях только там, где их разрешает протокол.
  - Быстрый SEARCH: по UID — без БД, UNSEEN — из памяти актора.
  - SELECT и UNSEEN из памяти актора: состояние открытых папок держит актор аккаунта, Postgres в этих командах не участвует (SELECT 220 + 140 → 99 мкс, UNSEEN 120 + 80 → 92 мкс, см. [bench/README.md](bench/README.md#select-и-unseen-из-памяти-актора)).
  - Таблица UID сессии хранится диапазонами.
  - MIME и BODYSTRUCTURE: дерево частей со смещениями разбирается при доставке, BODY/BODYSTRUCTURE отдаются без чтения тела, `BODY[1.2]`, `BODY[2.MIME]`, `BODY[3.HEADER]` режут сырые байты по смещениям.
- **TLS через HAProxy** (`deploy/haproxy`) и PROXY protocol v2 (сервер видит настоящий IP клиента), сертификат ECDSA.
- **Directory в ETS** и кеш успешных логинов.
- **Telemetry**; нагрузочные инструменты в `bench/`: `seed.exs`, `seed_folders.exs`, генератор `loadgen` со сценариями idle и poller, ключами `--tls` и `--until`.
- **Нагрузочные тесты нашли и исправили:**
  - простаивающий сокет держал чужой 400-килобайтный буфер Postgrex — переход на `{active, 100}`;
  - буфер Postgrex ограничен 64 KB;
  - SEARCH по UID ходил в БД;
  - в кеше справочника хранился лишний `DateTime`.
- **Ключевые цифры** (Mac mini, всё на одной машине):

  | Что | Значение |
  |---|---|
  | Память на сессию, папка из нескольких писем | ~6 KB |
  | Память на сессию, INBOX из 2 000 писем | 9,6–16,5 KB (зависит от числа удалённых) |
  | HAProxy на одно TLS-соединение | ~32–36 KB |
  | CPU сервера на команду | NOOP ~30 мкс, STATUS ~50 мкс |
  | Доставка письма из Kafka, пачками | ~0,2 мс CPU узла + ~0,1 мс Postgres (по одному: ~0,5 + ~1 мс) |
  | Справочник на ~860 тыс. аккаунтов | ~530 MB на ноду, поиск ~6,5 мкс |

- **Сравнение со Stalwart** v1.2.0 на тех же сценариях (стенд `bench/stalwart`, итоги в [bench/README.md](bench/README.md#сравнение-со-stalwart)):
  - Stalwart быстрее на командах: NOOP 30 против 75 мкс, SELECT и UNSEEN ~30 мкс и без Postgres против наших 220 + 140 мкс (он держит состояние папок в памяти; после переноса этого приёма у нас 99 мкс без Postgres);
  - память на простаивающую сессию 2,5 против 12,9 KB RSS;
  - доставка по одному письму стоила одинаково, ~1,6 мс CPU (сервер плюс Postgres); групповая запись из Kafka у нас — 0,3 мс;
  - кеша логинов у Stalwart нет, но с хешами SHA512-CRYPT из Dovecot вход стоит 1,2 мс;
  - модель хранения не подходит без доработок: все ноды на одном хранилище данных, шардирования данных по tenant нет ни в одной редакции, удаление по сроку — только Trash и Junk, приёма из Kafka нет.
- **Совместимость** (`compat/`, итоги в [compat/README.md](compat/README.md)):
  - Dovecot `imaptest`: 0 ошибок в скриптовых тестах и в 60-секундном стрессе;
  - миграция из Dovecot через imapsync: 375 писем, сверка каждого письма с Dovecot, включая ENVELOPE и BODYSTRUCTURE, — 0 расхождений;
  - mbsync, OfflineIMAP и imapflow проходят двустороннюю синхронизацию и сценарий сервиса;
  - Thunderbird (вручную): папки, письма и вложения, флаги, новое письмо во время IDLE, копия в Sent.
- 177 тестов, включая сквозной через Python imaplib, тесты на нескольких нодах и на двух шардах.

### Решения

- **Сроки хранения по политикам:** политики и сопоставление классов задаются в конфиге (или JSON в `MAILSTORE_RETENTION`). По умолчанию входящий warmup — 30 дней, остальное — 12 месяцев (сейчас в рабочей системе всё хранится 6 месяцев). Политика — отдельные партиции, её недели удаляются целиком.
- **Warmup остаётся в INBOX:** сервисы прогрева сами ищут свои письма во входящих.
- **Мастер-инбоксы открывают обычными почтовыми программами**, поэтому BODYSTRUCTURE и MIME обязательны. Парсер — на Elixir, при доставке, а не Rust NIF.
- **Проверка существования ящика** — на `RCPT TO` во входящем SMTP (множество адресов в быстром хранилище, ответ `550 5.1.1`) и окончательная — при записи в хранилище.
- **Шардирование по tenant.**
  - Шард = кластер Postgres (Patroni + PgBouncer) с синхронной репликой. Рекомендуемые настройки — `deploy/postgres/` (`shard.conf` и README с настройками таблиц на потом).
  - Реестр `shards` и `tenants.shard` лежат в справочнике, на нодах — кеш в ETS и пул на каждый шард (свой модуль репозитория на шард).
  - Перенос tenant без простоя: копирование без блокировок → заморозка (блокировка строк папок, через которые и так проходит каждая запись) с докопированием дельты по MODSEQ → пометка `fenced` на старом шарде → переключение `tenants.shard`.
- **TLS** — на HAProxy, порт 993, без STARTTLS.
- **Нативный разбор IMAP (NIF) не нужен:** разбор — единицы микросекунд из ~30 мкс раунда команды. CPU экономят ответы из памяти и знание профиля команд клиентов (см. «Как снизить CPU»).

### Дальше, по приоритету

1. **Профиль команд реальных клиентов** — чтобы собрать реалистичный сценарий poller.
2. **Кластер:**
   - **Плавная передача ящиков при смене состава.** Сейчас нода разом останавливает все акторы переехавших ящиков, и до 1/N активных ящиков одновременно перечитывают состояние папок из базы. Порциями их останавливать нельзя: пока жив старый актор, записи уже идут через новую ноду, и сессии на старом акторе не получают чужих изменений. Нужна такая схема:
     - новый владелец пересылает вызовы старому, пока там работает актор;
     - старая нода для пересланных вызовов не создаёт новых акторов;
     - уведомления о доставке идут обоим;
     - старая нода останавливает акторы порциями.
   - Нагрузочный прогон на нескольких нодах (Linux).
   - Поиск нод через DNS или оркестратор вместо списка в конфигурации.
   - Совместимость `:erpc` при поэтапном деплое: на всех нодах должен быть один и тот же `AccountServer`.
3. **Шарды, что осталось:**
   - выбор шарда для нового tenant: сейчас все новые tenant попадают на шард 1, если шард не указан явно;
   - перенос tenant запускать только с ноды кластера, потому что именно она рассылает остальным «tenant переехал»; утилита для оператора и прогон на объёме;
   - наполнять справочник из внешней системы учёта клиентов (клиенты, домены, ящики, мастер-инбоксы) через Kafka или CDC;
   - при переносе большого tenant заморозка растёт с дельтой, накопленной за время копирования; её можно сократить вторым проходом копирования перед заморозкой.
4. **Общий домен для мастер-инбоксов.** Сейчас у домена ровно один владелец (`domains.tenant_id NOT NULL`), и ящик берёт tenant у домена, поэтому один домен на всех клиентов для их мастер-инбоксов не завести. План:
   - домен без владельца (`tenant_id = NULL`);
   - при создании ящика в таком домене tenant указывается явно, в обычном домене он должен совпадать с tenant домена;
   - адрес по-прежнему уникален глобально.

   Шард, правила, перенос и удаление tenant уже идут по `accounts.tenant_id`, поэтому мастер-инбокс живёт на шарде своего клиента и переезжает вместе с ним.
5. **Холодный слой тел:** закрытые недели политик с `cold_after_days` → объектное хранилище (MinIO или S3), чтение через Range GET; словари zstd. Политики хранения уже есть (`Mailbox.Retention`, docs/architecture.md §7).
6. **Приём из Kafka на реальном потоке:** «тень» на рабочих топиках своей группой консьюмеров (это запись в чужой Kafka: группа и офсеты); признак класса `reply` от SMTP-слоя.
7. **Протокол и совместимость:** почтовые программы с GUI (Apple Mail, Outlook, мобильные; Thunderbird проверен); CONDSTORE/QRESYNC; ESEARCH, SORT/THREAD для веб-клиентов.
8. **Нагрузка на Linux:** 100 тыс. сессий, CPU и задержка TLS-рукопожатий, сценарий burst, память TLS в BEAM против HAProxy.
9. **Цена раунда команды:** NOOP стоит 75 мкс CPU против 30 у Stalwart.

### Открытые вопросы

- **Делать самим или брать Stalwart.** По CPU и памяти Stalwart лучше, но его модель хранения (одно хранилище данных на кластер, удаление по сроку только для Trash и Junk) не совпадает с нашей (шарды по tenant, `DROP` партиций по классам писем). Решает то, что этот стенд не мерил: Stalwart на FoundationDB с миллионом ящиков и цена удаления warmup по сроку.
- Схемы хешей паролей при импорте аккаунтов из существующего сервера (SHA512-CRYPT, BLF-CRYPT).
- Делают ли клиенты APPEND в Sent? Это удваивает объём хранения.
- **Допущение:** старые письма практически не читают, порядка одного на миллион. Логов чтения нет, это не замер. На нём держится холодный слой: чтение оттуда медленнее и не оптимизируется.
- Как отличать ответ (`reply`, идёт в мастер-инбокс) от прочих входящих: в записях топика есть `is_warmup`, `is_spamtest`, `is_followup`, но отдельного признака ответа нет.

### Как продолжить

```bash
docker compose up -d postgres            # Postgres 17 на :55432
mix test                                 # 177 тестов
deploy/haproxy/gen-cert.sh && docker compose up -d haproxy   # если нужен TLS на :10993
```

Тестовые данные для нагрузочных сценариев создают `bench/seed.exs` и `bench/seed_folders.exs`. Очистить: `mix ecto.reset` (удаляет и пересоздаёт справочник и базы всех шардов). Сертификат HAProxy генерируется скриптом и в репозитории не хранится.

## Запуск

```bash
docker compose up -d          # Postgres 17 на localhost:55432
mix setup                     # deps + справочник mailstore_dev + шард mailstore_dev_shard1 + миграции обоих (для NIF crc32cer клиента Kafka нужен cmake: brew install cmake)
mix test                      # 177 тестов: сквозной через Python imaplib, кластер из 2–3 нод (:peer), два шарда (база mailstore_test_shard2 создаётся сама)
mix mailstore.rules.import priv/delivery_rules/example.json    # правила доставки (реальный набор — локальный файл)
mix mailstore.migrate         # при деплое: справочник, начальный шард, все шарды (вместо mix ecto.migrate)
mix run priv/scripts/bench_delivery.exs -- --accounts 2000 --messages 50000 --concurrency 64
mix run --no-halt             # IMAP на 127.0.0.1:1143 (без TLS: TLS снимается на HAProxy)
MAILSTORE_KAFKA_HOSTS=localhost:9092 mix run --no-halt   # то же плюс приём из Kafka (стенд: bench/ingest)
```

Кластер из двух нод на одной машине (порт IMAP второй ноды — 1243):

```bash
MAILSTORE_IMAP_PORT=1143 MAILSTORE_CLUSTER_NODES=ms2@127.0.0.1 \
  elixir --name ms1@127.0.0.1 --cookie dev -S mix run --no-halt
MAILSTORE_IMAP_PORT=1243 MAILSTORE_CLUSTER_NODES=ms1@127.0.0.1 \
  elixir --name ms2@127.0.0.1 --cookie dev -S mix run --no-halt
```

Проверить любым клиентом, например curl:

```bash
curl --user "eve@example.test:pw" "imap://127.0.0.1:1143/INBOX" -X "SEARCH ALL"
```

Аккаунт для этого создаётся через `Mailstore.Directory.create_account(domain, "eve", %{password: "pw"})`.

TLS (через HAProxy, как в целевой схеме):

```bash
deploy/haproxy/gen-cert.sh    # самоподписанный ECDSA P-256 сертификат
docker compose up -d haproxy  # TLS на localhost:10993 → BEAM :1144 (PROXY protocol v2)
```

## Устройство

Диаграммы (развёртывание, дерево процессов, доставка, IMAP-сессия, схема данных, жизненный цикл письма) — в [docs/architecture.md](docs/architecture.md).

Структура по соглашению Phoenix contexts: у каждого контекста один публичный модуль (`lib/mailstore/<context>.ex`), а его схемы, запросы и внутренние модули лежат в одноимённой папке. Контексты обращаются друг к другу только через публичные модули.

```
lib/mailstore/
```

Тесты повторяют эту структуру: `test/mailstore/mailbox_test.exs` проверяет поведение через публичный API, а `test/mailstore/mailbox/*` — внутренние модули (жизненный цикл актора, гарантии БД, партиции).

## IMAP

`Imap.Session` — машина состояний без сокетов: на вход команда, на выход байты ответа. `Imap.Connection` владеет сокетом и передаёт в сессию команды и push-уведомления актора. Поэтому сессию можно тестировать без сети.

**Поддерживается** (по CAPABILITY): `IMAP4rev1 LITERAL+ IDLE UIDPLUS MOVE NAMESPACE ID ENABLE UNSELECT SPECIAL-USE CHILDREN`.

- Сессия: CAPABILITY, NOOP, LOGOUT, ID, LOGIN.
- Папки: LIST (с `\HasChildren`/`\HasNoChildren` и special-use), LSUB, STATUS, SELECT и EXAMINE (все из памяти актора), CREATE (с недостающими родителями), DELETE (папку с детьми — нет, как в Dovecot), RENAME (с поддеревом; UID и UIDVALIDITY сохраняются), SUBSCRIBE/UNSUBSCRIBE, NAMESPACE. Разделитель `/`, имена в modified UTF-7 хранятся как есть. UIDVALIDITY новой папки берётся из последовательности Postgres, поэтому пересозданная папка никогда не получает прежний.
- `\Recent` по RFC 3501: письмо недавнее ровно для одной сессии, открывшей папку на запись (EXAMINE его не забирает). Граница в памяти актора; он берёт её из `folders.recent_uid` при старте и записывает обратно при остановке, как `first_recent_uid` в индексе Dovecot. Ключевые слова, используемые в папке, перечислены в `* FLAGS`, новое объявляется до первого FETCH с ним.
- Письма: APPEND (APPENDUID), FETCH / UID FETCH, STORE / UID STORE (включая .SILENT), SEARCH / UID SEARCH, COPY / MOVE (COPYUID), EXPUNGE / UID EXPUNGE, CLOSE, UNSELECT, CHECK, IDLE.
- FETCH: UID, FLAGS, INTERNALDATE, RFC822.SIZE, ENVELOPE, BODY, BODYSTRUCTURE, RFC822[.HEADER|.TEXT], макросы ALL/FAST/FULL, BODY[] и BODY.PEEK[] с секциями HEADER, TEXT, HEADER.FIELDS[.NOT], номерами частей (`1.2`), их MIME/HEADER/TEXT и частичной выдачей `<n.m>`. Чтение без PEEK ставит `\Seen` и сообщает новые флаги.
- MIME (`Core.Mime`): дерево частей разбирается при доставке и хранится в `messages.bodystructure` (jsonb, короткие ключи: ~100 байт у text/plain, ~300 у multipart/alternative). Разбор стоит ~6 мкс на простое письмо и ~20 мкс на multipart/alternative. BODYSTRUCTURE отдаётся из метаданных одним запросом, секции частей режутся по смещениям из дерева. Формат ответа как у Dovecot: типы в нижнем регистре, параметры как в письме, продолжения RFC 2231 склеены. Защита от враждебных писем: глубина до 32, до 1 000 частей (остальные остаются внутри последней). Строки без дерева (записанные до парсера) получают его разбором тела при FETCH. Проверено сверкой с пакетом `email` из Python на 200 сгенерированных письмах (751 часть).
- SEARCH: флаги, KEYWORD, FROM/TO/CC/BCC/SUBJECT, HEADER, BODY, TEXT, LARGER/SMALLER, BEFORE/ON/SINCE, UID, наборы номеров, NOT, OR, скобки, CHARSET. Запросы только по UID и номерам отвечаются из таблицы UID сессии, UNSEEN — из памяти актора, оба без БД; остальные флаги — узкими строками без envelope.
- Таблица UID (`Core.UidMap`) хранит диапазоны подряд идущих UID и переходит на простой кортеж, если дыр слишком много: папка из 2 000 писем без удалений занимает ~200 байт.
- Состояние открытых папок в акторе аккаунта: все UID и непрочитанные, оба как `UidMap`. Загружается при первом SELECT за жизнь актора и дальше обновляется его же записями (APPEND, STORE, EXPUNGE) и уведомлениями групповой записи доставки, сбрасывается при COPY/MOVE в папку и после удаления по сроку. Уведомления от разных писателей могут прийти не по порядку: актор помнит первый UID, о котором ещё не сообщал, дочитывает из базы пропущенные (UID папки коммитятся по возрастанию) и пропускает запоздавшие. SELECT получает снимок вместе с подпиской, атомарно, поэтому окна, в котором можно пропустить изменение, нет.

**Push-уведомления.** Изменения от актора (новые письма, флаги, удаления) превращаются в нетегированные ответы только там, где это разрешает протокол: в конце команды и сразу во время IDLE. Во время FETCH, STORE и SEARCH без UID EXPUNGE не отправляется, чтобы номера не съехали у клиента. Если актор упал, сессия переподписывается и догоняет состояние: UID берёт из снимка нового актора, изменения флагов — из БД по MODSEQ.

**TLS.** Его снимает HAProxy (`deploy/haproxy`): неявный TLS на 993 по RFC 8314, кеш TLS-сессий для переподключений, сертификат ECDSA P-256. На BEAM передаётся открытый IMAP с заголовком PROXY protocol v2 на отдельный порт (`proxy_port`, 1144), так что сервер видит настоящий IP клиента. Соединение на этот порт без заголовка закрывается. STARTTLS на 143 нет: HAProxy не умеет его для IMAP, а клиенты ходят на 993.

**Directory в ETS** (`Directory.Cache`). Поиск получателя, LOGIN и правила маршрутизации идут без базы. Изменённые строки опрашиваются раз в секунду, полная перезагрузка раз в 10 минут убирает удалённые. Записи через `Directory` применяются сразу. Успешные логины кешируются на час как HMAC от хеша пароля и самого пароля; смена пароля их сбрасывает. На ~860 тыс. аккаунтов: ~530 MB на ноду, поиск ~6,5 мкс, полная загрузка 5–9 с.

**Пока нет:** BINARY (RFC 3516, декодирование base64/QP на сервере), поиск BODY/TEXT по декодированному тексту частей (сейчас — по сырым байтам), AUTHENTICATE, CONDSTORE / QRESYNC в протоколе (в хранилище MODSEQ уже есть), ESEARCH, SORT, THREAD, LIST-EXTENDED.

## Правила доставки

Что в классической схеме делает sieve-скрипт ящика в Dovecot, здесь делает `Core.Rules` при доставке. Правило — это данные: название, стадия, позиция, условие и действия. Хранятся в таблице `delivery_rules` справочника, на нодах лежат в кеше: в ETS, а глобальные ещё и в `persistent_term`. Правила бывают трёх уровней:
- `global` — для всех ящиков;
- `tenant` — для всех ящиков клиента, например его фильтры warmup;
- `account` — для одного ящика, например его `skip_sequence`.

При доставке правила всех уровней сливаются по `position`. Изменения через `Directory` применяются сразу, изменения прямо в таблице — за секунду, со следующим опросом кеша. Перегенерации скриптов нет. Пример правила:

```json
{"name": "VendorA", "stage": "detect", "position": 20,
 "test": {"any": [{"header": "Message-ID", "contains": "<vendor-a-", "case": "sensitive"},
                  {"header": "References", "contains": "<vendor-a-", "case": "sensitive"}]},
 "actions": [{"add_header": ["X-Warmup-Vendor", "VendorA"]}, {"set_class": "warmup"}, "stop"]}
```

- **Стадии.**
  - `detect` выполняется для каждого письма.
  - `forward` выполняется только у ящиков с правилами пересылки. Если ни одно правило в ней не остановило обработку, письмо пересылается в конце стадии, как в последнем `else` sieve.
- **Семантика как в Sieve.**
  - `stop` останавливает обработку.
  - Письмо сохраняется у получателя неявно, если `discard`, `redirect` или пересылка в режиме `redirect` этого не отменили.
  - Изменения заголовков видят только действия после них: `keep` и `forward` сохраняют письмо таким, каким оно было в этот момент.
- **Условия.**
  - Заголовок: `contains`, `is`, `matches`, `regex`, `contains_any`, `regex_any`, `exists`. Значения раскодированы по RFC 2047.
  - Тело: те же операции по каждой раскодированной текстовой части; HTML остаётся HTML.
  - Комбинации `any`, `all`, `not`, а также `class`.
  - Регистр по умолчанию не учитывается (`i;ascii-casemap`); `"case": "sensitive"` соответствует `i;octet`.
  - Группы регулярного выражения по заголовку (`"capture": true`) можно подставлять как `${1}` в следующие условия; при подстановке они экранируются.
  - Регулярные выражения PCRE, `$` означает конец строки. Число шагов ограничено, поэтому патологический шаблон считается несовпадением, а не вешает доставку.
- **Действия.** `keep`, `discard`, `stop`, `redirect`, `forward` (с заголовками только для копий), `add_header` (сверху, как `addheader`), `set_header`, `delete_header`, `set_class`, `notify`. В значениях можно использовать `${from_address}`, `${to_address}` и `${message_id}`.
- **Перенос существующего sieve.** Правила sieve-скрипта переносятся в JSON один в один, например: отказы уходят в ящик для отказов; правила по поставщикам warmup ставят тег и класс `warmup`, такие письма не пересылаются; часть меток удаляет письмо; в стадии пересылки автоответы и одна формулировка недоставки остаются во входящих, остальное пересылается, и копия получает заголовок с исходным отправителем. Реальный набор и тест на каждое его правило хранятся в каталогах `local/` (`priv/delivery_rules/local/`, `test/local/`), которые git игнорирует; формат показан в `priv/delivery_rules/example.json`. Фильтры ящиков из sieve переносятся правилами `tenant` и `account` на позиции 2000.
- **Чего нет по сравнению с sieve.**
  - Хуков CRM и перезаписи `To` для пересылки во внешние CRM: для неё нужна исходящая отправка.
  - Пропуска распознавания на хабах: копии кладутся прямо в ящик и повторно правила не проходят.
  - Тег поставщика у нас ещё и ставит класс `warmup` (срок хранения, фильтр мастер-инбокса). Sieve только добавлял заголовок.
- **Цена.** Около 60 мкс CPU на письмо, когда выполняются все правила, и 27–40 мкс, если раньше срабатывает правило по заголовку. Дерево MIME разбирается один раз на письмо. Копии с добавленными заголовками строятся сдвигом смещений, без повторного разбора. На стенде Kafka это +65 мкс CPU узла на письмо при разборе очереди (`bench/README.md`).

## Наблюдаемость и нагрузка

`Mailstore.Telemetry` публикует события `[:mailstore, :imap, :connection, :open | :close]` и span `[:mailstore, :imap, :command, ...]` на каждую команду IMAP (с её именем и статусом). `CommandStats` агрегирует их в ETS: число, среднее время, гистограмма. `Telemetry.snapshot/1` отдаёт память VM, процессы, соединения, акторы и статистику команд. Его читает нагрузочный генератор. С `MAILSTORE_REPORT_MS=5000` сервер пишет строку отчёта в лог.

Простаивающие соединения уходят в гибернацию через `hibernate_after` (15 с). Сокеты работают в режиме `{active, 100}`: в простое у них нет буфера чтения.

**Сценарий idle** (`bench/`), Mac mini, всё на одной машине: 10 000 сессий LOGIN + SELECT + IDLE, ошибок 0, установка p99 = 57 мс, **~6 KB на сессию** в установившемся режиме, весь сервер — 118 MB. С реальными папками (INBOX по 2 000 писем) — 9,6 KB на сессию без удалений и 14 KB при 10% удалённых, включая актор аккаунта. Тест нашёл проблему: перевзвод `{active, :once}` заставлял каждый простаивающий сокет держать буфер чтения, а из кеша драйвера inet ему доставался бывший 400-килобайтный буфер Postgrex. Исправлено: соединения используют `{active, 100}`, буфер Postgrex ограничен 64 KB. Подробности в [bench/README.md](bench/README.md).

**Сценарий poller** (постоянные сессии, цикл команд, параллельно доставки): протокольный раунд стоит ~30 мкс CPU, STATUS из памяти актора ~50 мкс, `UID SEARCH UID n:*` ~70 мкс на сервере плюс ~90 мкс в Postgres, доставка ~0,5 мс плюс ~1 мс в Postgres. Дорого всё, что ходит в БД. После быстрых путей `UID SEARCH UID n:*` отвечает из таблицы UID сессии и стоит как NOOP: Postgres 0,75 → 0,01 ядра, p99 262 → 8 мс при 5 000 поисков в секунду.

## Оценка хранения

По схеме прототипа одно письмо занимает ~1,5 KB: метаданные с индексами ~0,7 KB плюс тело ~2 KB, сжатое zstd до ~0,8 KB. Объём считается как «писем в сутки × срок хранения × 1,5 KB», с репликой — вдвое больше. Пример: 10 млн писем в сутки при сроке 6 месяцев — ~1,8 млрд писем, ~2,7 TB на primary.

Как снизить, по убыванию эффекта:
1. Тела писем из закрытых недельных партиций (старше ~2 недель) выносить в объектное хранилище упакованными файлами: HDD с erasure coding, ×1,4 вместо NVMe ×2. Закрытая неделя неизменяема, так что это ложится на текущую схему партиций.
2. zstd со словарём для warmup: тексты шаблонные, тело станет ~0,3–0,4 KB.
3. Для старого warmup не хранить envelope, а вычислять его из тела, если клиент попросит.

С 1–3 на NVMe остаются в основном метаданные, а тела переезжают на дешёвые диски.

## Как снизить CPU

BEAM на команду IMAP тратит больше CPU, чем C-сервер вроде Dovecot. Выигрыш схемы — в архитектуре (общий кластер вместо запаса на каждом сервере, масштабирование вычислений и хранения по отдельности), а не в языке. Что снижает CPU, по убыванию эффекта:

| Мера | Ожидаемый эффект |
|---|---|
| Узнать профиль команд реальных клиентов | задаёт горячий путь, без него оптимизация вслепую |
| SELECT, STATUS, UNSEEN из памяти сессии или ETS, без актора и БД | основной выигрыш; `UID SEARCH UID n:*` так уже подешевел до уровня NOOP |
| Одна запись в сокет на ответ, telemetry по выборке, `:socket` вместо `gen_tcp`, настройка `hibernate_after` | проценты, мерить |
| IDLE вместо опроса, ограничение слишком частого опроса | зависит от клиентов, потенциально кратно |
| kTLS в HAProxy | 10–30% от TLS-части, проверить поддержку |
| NIF для разбора IMAP | 5–10% от команд, плюс риск уронить ноду — не делать |
| Нативный IMAP целиком (свой на Rust или Stalwart) | уровень Dovecot, но без преимуществ BEAM |

## Схема

Две базы и две схемы миграций: справочник (`Mailstore.Repo`, `priv/repo/migrations`) и шард (`priv/shard/migrations`, на каждом шарде своя `schema_migrations`). Между ними нет ни внешних ключей, ни общих транзакций.

**Directory** (`priv/repo/migrations/*_create_directory.exs`): `tenants` (с полем `shard`), `domains`, `accounts` (`kind`: mailbox / master_inbox), `forwardings` (copy / redirect, `only_classes`, чтобы warmup не попадал в мастер-инбокс).

**Реестр шардов** (`priv/repo/migrations/*_create_shards.exs`): `shards` (`id`, `name`, `url`, `pool_size`), `tenants.shard` ссылается на него.

**Шард** (`priv/shard/migrations/*_create_mail.exs` и следующие). `folders.fenced` — папки tenant, перенесённого на другой шард.

- `folders`: пространство UID папки (`uidvalidity`, `uidnext`, `highest_modseq`), счётчики `messages_count` / `unseen_count`. Счётчики обновляются тем же `UPDATE`, который выделяет UID, поэтому STATUS никогда не сканирует письма.
- `messages`: узкая таблица метаданных, партиционирована по политике хранения (`retention`), внутри — по неделям `stored_at`. Индексы:
  - `(folder_id, modseq)` — для CONDSTORE;
  - частичный `(folder_id, uid) WHERE NOT \Seen` — главный запрос поллеров;
  - `(tenant_id, message_id_h)` — Message-ID и треды.
- `message_bodies`: сырые байты RFC 5322, сжатые zstd на стороне приложения. Письма около 2 KB, это ниже порога TOAST, так что Postgres сам бы их не сжал. Тела вынесены в отдельную таблицу, чтобы сканирование флагов не читало их.
- `vanished`: удалённые UID для QRESYNC.
- `deliveries`: ключи уже доставленного для идемпотентного приёма, дневные партиции, хранятся `delivery_dedup_days` (8 дней, дольше хранения исходных топиков).

**Справочник, правила доставки** (`*_create_delivery_rules.exs`): `delivery_rules` (`scope` global / tenant / account, `stage`, `position`, `name`, `spec` с условием и действиями, `enabled`).

**Почему UID не задвоятся при двух акторах (netsplit):** UID выдаются атомарным `UPDATE folders ... RETURNING`, а флаги и expunge блокируют строку папки через `FOR UPDATE`. Это проверяет тест «split brain». Уникального ограничения на `(folder_id, uid)` по всем партициям нет: Postgres требует включать ключ партиции в уникальные индексы. Гарантию даёт именно выделение UID.

## Что проверяют тесты

- Одновременный старт: 20 конкурентных `ensure` дают один актор.
- Шарды (вторая база `mailstore_test_shard2`):
  - письма tenant лежат на его шарде, id папок — из диапазона шарда;
  - перенос tenant, пока параллельно идут доставка с ключами и STORE: все письма на новом шарде ровно по разу, UID без дыр, флаги и счётчики папок совпадают, подписанная сессия переподписывается, повтор доставки опознаётся, старый шард помечен и очищается;
  - APPEND через IMAP, попавший на переключение, повторяется на новом шарде.
- Кластер (вторая и третья нода через `:peer`, общая тестовая база):
  - актор ящика работает только на владельце, доставка и APPEND с другой ноды доходят до подписчиков;
  - клиент IMAP в IDLE на одной ноде получает `* 1 EXISTS` о письме, доставленном на другой;
  - нода уходит — её ящики переезжают, сессии переподписываются; нода приходит — ей передаются ящики, которые она теперь выигрывает.
- 100 конкурентных append дают UID 1..100 без дыр, счётчики корректны.
- Запись мимо актора (имитация split-brain) не даёт коллизий UID.
- Подписчик получает EXISTS / FLAGS / EXPUNGE. Повторный STORE без изменений не создаёт новый MODSEQ.
- MOVE переносит байты, выдаёт новые UID и удаляет исходные письма в одной транзакции.
- Актор останавливается по idle-таймауту, но не пока есть подписчик. Вызов, который попал на остановку актора, повторяется на новом.
- Доставка: reply попадает в мастер-инбокс, warmup не попадает; redirect не сохраняет оригинал.
- Групповая запись: пачка на несколько аккаунтов даёт UID подряд в каждой папке; повтор пачки ничего не пишет и не тратит UID; ключ, записанный в прошлый день, тоже дубль; уведомления не по порядку и запоздавшие дают сессии каждый UID один раз и по возрастанию; `\Recent` переживает перезапуск актора.
- Приём: разбор записи топика (класс, получатель, ключ, ошибки), конвейер на `Broadway.DummyProducer`: пачка записана, повтор опознан, нечитаемая запись ушла в dead letter.
- Правила доставки:
  - семантика движка: `stop`, неявное сохранение, снимки при `keep` и `forward`, `discard` и `redirect`, режимы пересылки, захваты с экранированием, регистр, RFC 2047, раскодированные части, ограничение регулярных выражений, отказ на неверных правилах;
  - локальный тест (`test/local/`) проверяет каждое правило реального набора на синтетическом письме, похожие письма правило не задевают;
  - интеграция: тег и класс warmup, удаление, отказ во внешний или свой ящик, фильтр ящика не пускает письмо в мастер-инбокс, изменения правил применяются без перезапуска.
- Удаление недельной партиции сдвигает `retained_from_uid` и поднимает `highest_modseq`.
- IMAP-протокол: framing с синхронными литералами и LITERAL+, разбор команд, наборы номеров (включая `n:*` за последним письмом), ENVELOPE, даты.
- IMAP-сессия без сети: LOGIN, SELECT, FETCH (PEEK не меняет `\Seen`, BODY[] меняет), STORE, SEARCH, APPEND с литералом, COPY/MOVE с COPYUID, EXPUNGE с перенумерацией, read-only EXAMINE. Push: IDLE получает новое письмо сразу; чужой EXPUNGE откладывается во время FETCH и приходит после NOOP; при падении актора сессия догоняет состояние.
- Сквозной тест по TCP настоящим клиентом, Python `imaplib` (`test/imaplib/client.py`): login, list, select, append, fetch, store, search, copy, move, expunge и IDLE, пока тест доставляет письмо через `Delivery`.
- Быстрый SEARCH: по UID, номерам и UNSEEN — ноль запросов в БД, повторный SELECT тоже; `EXISTS` уходит до результата поиска.
- Состояние папок в памяти актора совпадает с базой после 60 случайных записей (APPEND, STORE ±`\Seen`, EXPUNGE, MOVE); после удаления по сроку перечитывается.
- `UidMap` сверяется со списковой моделью на 300 случайных операциях: добавление, вставка в середину, удаление (задействованы оба представления); память растёт с дырами, а не с письмами.
- Кеш справочника: чтения без БД, изменения в обход `Directory` подхватываются опросом, смена пароля сбрасывает кеш логинов, жёстко удалённые строки исчезают при полной перезагрузке.
- Порт для HAProxy: IP клиента берётся из заголовка PROXY, соединение без заголовка закрывается.
- Telemetry: счётчики команд по статусам, снимок видит соединения и их память.

## Бенчмарк доставки (Mac mini, Postgres в Docker)

```
delivered 50000 messages in 14.4 s = 3472 msg/s     (одна транзакция на письмо, 64 потока)
body bytes: raw 89 MB, stored 9.5 MB (9.4x)
```

Сжатие 9,4× завышено: в бенчмарке тело письма — повторяющаяся строка. Реальное сжатие нужно мерить на выгрузке настоящих писем.
