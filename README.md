# mailstore — прототип хранилища почты на Elixir

Прототип IMAP-кластера: IMAP4rev1-сервер поверх слоя хранения и координации. Вычисления (BEAM-ноды без состояния) отделены от хранения (шарды Postgres), поэтому их можно масштабировать по отдельности, а ящики не привязаны к конкретному серверу.

Целевой профиль — сотни тысяч или миллион ящиков и десятки миллионов писем в сутки, в основном небольшие автоматические письма (warmup) и ответы; ящики опрашивают сервисы по IMAP, мастер-инбоксы открывают обычными почтовыми программами. Диаграммы архитектуры — в [docs/architecture.md](docs/architecture.md), все замеры — в [bench/README.md](bench/README.md).

## Статус (25.11.2026)

### Сделано

- **Хранилище.**
  - Справочник (tenants, домены, аккаунты, правила пересылки) и шард (папки, метаданные писем, тела, журнал удалений).
  - Недельные партиции, удаление по сроку хранения через `DROP` партиции.
  - Актор аккаунта: выдаёт UID и MODSEQ, рассылает изменения сессиям.
  - Доставка с копией в мастер-инбокс, redirect и внешней пересылкой.
- **IMAP4rev1-сервер.**
  - Команды: LOGIN, LIST, STATUS, SELECT/EXAMINE, APPEND, FETCH, STORE, SEARCH, COPY/MOVE, EXPUNGE, IDLE (и UID-варианты), UIDPLUS.
  - Уведомления об изменениях только там, где их разрешает протокол.
  - Быстрый SEARCH: по UID — без БД, UNSEEN — по индексу.
  - Таблица UID сессии хранится диапазонами.
  - MIME и BODYSTRUCTURE: дерево частей со смещениями разбирается при доставке, BODY/BODYSTRUCTURE отдаются без чтения тела, `BODY[1.2]`, `BODY[2.MIME]`, `BODY[3.HEADER]` режут сырые байты по смещениям.
- **TLS через HAProxy** (`deploy/haproxy`) и PROXY protocol v2 (сервер видит настоящий IP клиента), сертификат ECDSA.
- **Directory в ETS** и кеш успешных логинов.
- **Telemetry**; нагрузочные инструменты в `bench/`: `seed.exs`, `seed_folders.exs`, генератор `loadgen` со сценариями idle и poller, ключами `--tls` и `--until`.
- **Нагрузочные тесты нашли и исправили:**
  - простаивающий сокет держал чужой 400-килобайтный буфер Postgrex — переход на `{active, 100}`;
  - буфер Postgrex ограничен 64 KB;
  - SEARCH по UID ходил в БД;
  - в кеше справочника хранился лишний `DateTime`.
- **Ключевые цифры** (Mac mini, всё на одной машине):

  | Что | Значение |
  |---|---|
  | Память на сессию, папка из нескольких писем | ~6 KB |
  | Память на сессию, INBOX из 2 000 писем | 9,6–16,5 KB (зависит от числа удалённых) |
  | HAProxy на одно TLS-соединение | ~32–36 KB |
  | CPU сервера на команду | NOOP ~30 мкс, STATUS ~50 мкс |
  | Доставка письма | ~0,5 мс CPU сервера + ~1 мс Postgres |
  | Справочник на ~860 тыс. аккаунтов | ~530 MB на ноду, поиск ~6,5 мкс |

- **Сравнение со Stalwart** v1.2.0 на тех же сценариях (стенд `bench/stalwart`, итоги в [bench/README.md](bench/README.md#сравнение-со-stalwart)):
  - Stalwart быстрее на командах: NOOP 30 против 75 мкс, SELECT и UNSEEN ~30 мкс и без Postgres против 220 + 140 мкс (он держит состояние папок в памяти);
  - память на простаивающую сессию 2,5 против 12,9 KB RSS;
  - доставка стоит одинаково, ~1,6 мс CPU на письмо (сервер плюс Postgres);
  - кеша логинов у Stalwart нет, но с хешами SHA512-CRYPT из Dovecot вход стоит 1,2 мс;
  - модель хранения не подходит без доработок: все ноды на одном хранилище данных, шардирования данных по tenant нет ни в одной редакции, удаление по сроку — только Trash и Junk, приёма из Kafka нет.
- 75 тестов, включая сквозной через Python imaplib.

### Решения

- **Сроки хранения по классам писем:** warmup хранится меньше, ответы дольше (например, 6 и 12 месяцев). Классы — отдельные партиции, удаляются целиком.
- **Warmup остаётся в INBOX:** сервисы прогрева сами ищут свои письма во входящих.
- **Мастер-инбоксы открывают обычными почтовыми программами**, поэтому BODYSTRUCTURE и MIME обязательны. Парсер — на Elixir, при доставке, а не Rust NIF.
- **Проверка существования ящика** — на `RCPT TO` во входящем SMTP (множество адресов в быстром хранилище, ответ `550 5.1.1`) и окончательная — при записи в хранилище.
- **Шардирование по tenant.**
  - Шард = кластер Postgres (Patroni + PgBouncer).
  - Реестр `shards` и `tenants.shard_id` лежат в справочнике, на нодах — кеш в ETS и пул на каждый шард (dynamic repo).
  - Перенос tenant без простоя: копия закрытых недель → заморозка на секунды → докопирование текущей недели → переключение `shard_id`.
- **TLS** — на HAProxy, порт 993, без STARTTLS.
- **Нативный разбор IMAP (NIF) не нужен:** разбор — единицы микросекунд из ~30 мкс раунда команды. CPU экономят ответы из памяти и знание профиля команд клиентов (см. «Как снизить CPU»).

### Дальше, по приоритету

1. **Профиль команд реальных клиентов** — чтобы собрать реалистичный сценарий poller.
2. **Шарды в прототипе:** таблица `shards`, dynamic repos, перенос tenant, тест на двух шардах.
3. **Холодный слой тел** (закрытые недели → объектное хранилище), классы хранения, словари zstd.
4. **Консьюмер очереди входящих** (Broadway); group commit в акторе.
5. **Протокол и совместимость:** CONDSTORE/QRESYNC, CREATE/RENAME/DELETE папок; Dovecot `imaptest`; Thunderbird, Apple Mail.
6. **Нагрузка на Linux:** 100 тыс. сессий, CPU и задержка TLS-рукопожатий, сценарий burst, память TLS в BEAM против HAProxy.
7. **SELECT и UNSEEN из памяти актора:** у Stalwart так и сделано, и эти команды у него в 4–8 раз дешевле и не нагружают Postgres.

### Открытые вопросы

- **Делать самим или брать Stalwart.** По CPU и памяти Stalwart лучше, но его модель хранения (одно хранилище данных на кластер, удаление по сроку только для Trash и Junk) не совпадает с нашей (шарды по tenant, `DROP` партиций по классам писем). Решает то, что этот стенд не мерил: Stalwart на FoundationDB с миллионом ящиков и цена удаления warmup по сроку.
- Схемы хешей паролей при импорте аккаунтов из существующего сервера (SHA512-CRYPT, BLF-CRYPT).
- Делают ли клиенты APPEND в Sent? Это удваивает объём хранения.

### Как продолжить

```bash
docker compose up -d postgres            # Postgres 17 на :55432
mix test                                 # 75 тестов
deploy/haproxy/gen-cert.sh && docker compose up -d haproxy   # если нужен TLS на :10993
```

Тестовые данные для нагрузочных сценариев создают `bench/seed.exs` и `bench/seed_folders.exs`. Очистить: `mix ecto.reset`. Сертификат HAProxy генерируется скриптом и в репозитории не хранится.

## Запуск

```bash
docker compose up -d          # Postgres 17 на localhost:55432
mix setup                     # deps + создание БД + миграции
mix test                      # 75 тестов, включая сквозной через Python imaplib
mix run priv/scripts/bench_delivery.exs -- --accounts 2000 --messages 50000 --concurrency 64
mix run --no-halt             # IMAP на 127.0.0.1:1143 (без TLS: TLS снимается на HAProxy)
```

Проверить любым клиентом, например curl:

```bash
curl --user "eve@example.test:pw" "imap://127.0.0.1:1143/INBOX" -X "SEARCH ALL"
```

Аккаунт для этого создаётся через `Mailstore.Directory.create_account(domain, "eve", %{password: "pw"})`.

TLS (через HAProxy, как в целевой схеме):

```bash
deploy/haproxy/gen-cert.sh    # самоподписанный ECDSA P-256 сертификат
docker compose up -d haproxy  # TLS на localhost:10993 → BEAM :1144 (PROXY protocol v2)
```

## Устройство

Диаграммы (развёртывание, дерево процессов, доставка, IMAP-сессия, схема данных, жизненный цикл письма) — в [docs/architecture.md](docs/architecture.md).

Структура по соглашению Phoenix contexts: у каждого контекста один публичный модуль (`lib/mailstore/<context>.ex`), а его схемы, запросы и внутренние модули лежат в одноимённой папке. Контексты обращаются друг к другу только через публичные модули.

```
lib/mailstore/
├── core/                      чистые функции: без БД и процессов
│   ├── headers.ex             разбор заголовков RFC 5322
│   ├── mime.ex                дерево MIME-частей со смещениями (BODYSTRUCTURE, BODY[n.m])
│   ├── new_message.ex         письмо, подготовленное к записи (разобрано один раз)
│   ├── flags.ex               флаги IMAP ↔ битовая маска
│   ├── message_class.ex       warmup / reply / bounce / ...
│   └── body_codec.ex          сжатие zstd
│
├── directory.ex               КОНТЕКСТ: tenants, домены, аккаунты, правила пересылки
├── directory/
│   ├── schemas/               tenant, domain, account, forwarding
│   └── queries.ex             запросы Ecto (только строят запрос, выполняет контекст)
│
├── mailbox.ex                 КОНТЕКСТ: папки и письма аккаунта на его шарде
├── mailbox/
│   ├── schemas/               folder, message, message_body, vanished
│   ├── queries.ex             чтение (Ecto-запросы)
│   ├── commands.ex            запись (SQL: append, store_flags, expunge, copy)
│   ├── account_server.ex      актор аккаунта
│   ├── partitions.ex          недельные партиции и удаление по сроку хранения
│   ├── partition_maintainer.ex
│   └── supervisor.ex          дерево процессов контекста
│
├── delivery.ex                КОНТЕКСТ: маршрутизация входящего письма (замена LMTP + sieve)
│
├── imap.ex                    КОНТЕКСТ: IMAP-сервер (ranch listener)
├── imap/
│   ├── connection.ex          процесс на соединение: сокет, push-уведомления актора
│   ├── framing.ex             нарезка потока байтов на команды (литералы {n} и {n+})
│   ├── parser.ex              команда → tag, имя, аргументы
│   ├── session.ex             машина состояний сессии, без сокетов
│   ├── fetch.ex, search.ex    FETCH и SEARCH
│   ├── sequence_set.ex        1:3,5,7:*
│   ├── uid_map.ex             seq → UID этой сессии
│   └── format.ex              строки, флаги, даты, ENVELOPE
│
├── telemetry.ex               события :telemetry, статистика команд, снимок VM
├── telemetry/                 command_stats.ex (ETS-счётчики), reporter.ex (строка в лог)
│
├── repo.ex, schema.ex
└── shards.ex                  tenant → repo шарда (единственная связка directory и хранилища)

bench/                         нагрузочные тесты, не входят в сервер (см. bench/README.md)
├── seed.exs                   заливка аккаунтов
└── loadgen/                   отдельный Mix-проект: генератор IMAP-сессий
```

| Контекст | Публичный API | Внутреннее устройство |
|---|---|---|
| `Directory` | создание tenant / домена / аккаунта, `lookup_account`, `forwardings_for(account, class)` | `Schemas.*`, `Queries` |
| `Mailbox` | запись: `append`, `store_flags`, `expunge`, `copy`, `move`, `subscribe`, `status` (через актор); чтение: `uids`, `fetch_meta`, `fetch_raw`, `changed_since`, `vanished_since` (напрямую из шарда); `drop_partitions_before` | `AccountServer`, `Commands`, `Queries`, `Schemas.*`, `Partitions` |
| `Delivery` | `deliver(raw, rcpt, class: ...)` | использует только API `Directory` и `Mailbox` |
| `Imap` | listener (`child_spec`, `port`) | `Connection`, `Framing`, `Parser`, `Session`, `Fetch`, `Search`, `SequenceSet`, `UidMap`, `Format`; снаружи использует только `Directory.authenticate` и `Mailbox` |

Чтение и запись разведены специально. Чтение — это композируемые Ecto-запросы в `Queries`. Запись — явный SQL в `Commands`: там CTE и `FOR UPDATE`, которые на Ecto DSL читаются хуже.

Тесты повторяют эту структуру: `test/mailstore/mailbox_test.exs` проверяет поведение через публичный API, а `test/mailstore/mailbox/*` — внутренние модули (жизненный цикл актора, гарантии БД, партиции).

## IMAP

`Imap.Session` — машина состояний без сокетов: на вход команда, на выход байты ответа. `Imap.Connection` владеет сокетом и передаёт в сессию команды и push-уведомления актора. Поэтому сессию можно тестировать без сети.

**Поддерживается** (по CAPABILITY): `IMAP4rev1 LITERAL+ IDLE UIDPLUS MOVE NAMESPACE ID ENABLE UNSELECT SPECIAL-USE CHILDREN`.

- Сессия: CAPABILITY, NOOP, LOGOUT, ID, LOGIN.
- Папки: LIST, LSUB, STATUS (из памяти актора), SELECT, EXAMINE, SUBSCRIBE/UNSUBSCRIBE (no-op), NAMESPACE.
- Письма: APPEND (APPENDUID), FETCH / UID FETCH, STORE / UID STORE (включая .SILENT), SEARCH / UID SEARCH, COPY / MOVE (COPYUID), EXPUNGE / UID EXPUNGE, CLOSE, UNSELECT, CHECK, IDLE.
- FETCH: UID, FLAGS, INTERNALDATE, RFC822.SIZE, ENVELOPE, BODY, BODYSTRUCTURE, RFC822[.HEADER|.TEXT], макросы ALL/FAST/FULL, BODY[] и BODY.PEEK[] с секциями HEADER, TEXT, HEADER.FIELDS[.NOT], номерами частей (`1.2`), их MIME/HEADER/TEXT и частичной выдачей `<n.m>`. Чтение без PEEK ставит `\Seen` и сообщает новые флаги.
- MIME (`Core.Mime`): дерево частей разбирается при доставке и хранится в `messages.bodystructure` (jsonb, короткие ключи: ~100 байт у text/plain, ~300 у multipart/alternative). Разбор стоит ~6 мкс на простое письмо и ~20 мкс на multipart/alternative. BODYSTRUCTURE отдаётся из метаданных одним запросом, секции частей режутся по смещениям из дерева. Формат ответа как у Dovecot: типы в нижнем регистре, параметры как в письме, продолжения RFC 2231 склеены. Защита от враждебных писем: глубина до 32, до 1 000 частей (остальные остаются внутри последней). Строки без дерева (записанные до парсера) получают его разбором тела при FETCH. Проверено сверкой с пакетом `email` из Python на 200 сгенерированных письмах (751 часть).
- SEARCH: флаги, KEYWORD, FROM/TO/CC/BCC/SUBJECT, HEADER, BODY, TEXT, LARGER/SMALLER, BEFORE/ON/SINCE, UID, наборы номеров, NOT, OR, скобки, CHARSET. Запросы только по UID и номерам отвечаются без БД, UNSEEN — одним запросом по частичному индексу, флаги — узкими строками без envelope.
- Таблица UID сессии (`Imap.UidMap`) хранит диапазоны подряд идущих UID и переходит на простой кортеж, если дыр слишком много: папка из 2 000 писем без удалений занимает ~200 байт.

**Push-уведомления.** Изменения от актора (новые письма, флаги, удаления) превращаются в нетегированные ответы только там, где это разрешает протокол: в конце команды и сразу во время IDLE. Во время FETCH, STORE и SEARCH без UID EXPUNGE не отправляется, чтобы номера не съехали у клиента. Если актор упал, сессия переподписывается и догоняет состояние из БД.

**TLS.** Его снимает HAProxy (`deploy/haproxy`): неявный TLS на 993 по RFC 8314, кеш TLS-сессий для переподключений, сертификат ECDSA P-256. На BEAM передаётся открытый IMAP с заголовком PROXY protocol v2 на отдельный порт (`proxy_port`, 1144), так что сервер видит настоящий IP клиента. Соединение на этот порт без заголовка закрывается. STARTTLS на 143 нет: HAProxy не умеет его для IMAP, а клиенты ходят на 993.

**Directory в ETS** (`Directory.Cache`). Поиск получателя, LOGIN и правила маршрутизации идут без базы. Изменённые строки опрашиваются раз в секунду, полная перезагрузка раз в 10 минут убирает удалённые. Записи через `Directory` применяются сразу. Успешные логины кешируются на час как HMAC от хеша пароля и самого пароля; смена пароля их сбрасывает. На ~860 тыс. аккаунтов: ~530 MB на ноду, поиск ~6,5 мкс, полная загрузка 5–9 с.

**Пока нет:** BINARY (RFC 3516, декодирование base64/QP на сервере), поиск BODY/TEXT по декодированному тексту частей (сейчас — по сырым байтам), CREATE / DELETE / RENAME папок, AUTHENTICATE, CONDSTORE / QRESYNC в протоколе (в хранилище MODSEQ уже есть), имена папок в modified UTF-7.

## Наблюдаемость и нагрузка

`Mailstore.Telemetry` публикует события `[:mailstore, :imap, :connection, :open | :close]` и span `[:mailstore, :imap, :command, ...]` на каждую команду IMAP (с её именем и статусом). `CommandStats` агрегирует их в ETS: число, среднее время, гистограмма. `Telemetry.snapshot/1` отдаёт память VM, процессы, соединения, акторы и статистику команд. Его читает нагрузочный генератор. С `MAILSTORE_REPORT_MS=5000` сервер пишет строку отчёта в лог.

Простаивающие соединения уходят в гибернацию через `hibernate_after` (15 с). Сокеты работают в режиме `{active, 100}`: в простое у них нет буфера чтения.

**Сценарий idle** (`bench/`), Mac mini, всё на одной машине: 10 000 сессий LOGIN + SELECT + IDLE, ошибок 0, установка p99 = 57 мс, **~6 KB на сессию** в установившемся режиме, весь сервер — 118 MB. С реальными папками (INBOX по 2 000 писем) — 9,6 KB на сессию без удалений и 14 KB при 10% удалённых, включая актор аккаунта. Тест нашёл проблему: перевзвод `{active, :once}` заставлял каждый простаивающий сокет держать буфер чтения, а из кеша драйвера inet ему доставался бывший 400-килобайтный буфер Postgrex. Исправлено: соединения используют `{active, 100}`, буфер Postgrex ограничен 64 KB. Подробности в [bench/README.md](bench/README.md).

**Сценарий poller** (постоянные сессии, цикл команд, параллельно доставки): протокольный раунд стоит ~30 мкс CPU, STATUS из памяти актора ~50 мкс, `UID SEARCH UID n:*` ~70 мкс на сервере плюс ~90 мкс в Postgres, доставка ~0,5 мс плюс ~1 мс в Postgres. Дорого всё, что ходит в БД. После быстрых путей `UID SEARCH UID n:*` отвечает из таблицы UID сессии и стоит как NOOP: Postgres 0,75 → 0,01 ядра, p99 262 → 8 мс при 5 000 поисков в секунду.

## Оценка хранения

По схеме прототипа одно письмо занимает ~1,5 KB: метаданные с индексами ~0,7 KB плюс тело ~2 KB, сжатое zstd до ~0,8 KB. Объём считается как «писем в сутки × срок хранения × 1,5 KB», с репликой — вдвое больше. Пример: 10 млн писем в сутки при сроке 6 месяцев — ~1,8 млрд писем, ~2,7 TB на primary.

Как снизить, по убыванию эффекта:
1. Тела писем из закрытых недельных партиций (старше ~2 недель) выносить в объектное хранилище упакованными файлами: HDD с erasure coding, ×1,4 вместо NVMe ×2. Закрытая неделя неизменяема, так что это ложится на текущую схему партиций.
2. zstd со словарём для warmup: тексты шаблонные, тело станет ~0,3–0,4 KB.
3. Для старого warmup не хранить envelope, а вычислять его из тела, если клиент попросит.

С 1–3 на NVMe остаются в основном метаданные, а тела переезжают на дешёвые диски.

## Как снизить CPU

BEAM на команду IMAP тратит больше CPU, чем C-сервер вроде Dovecot. Выигрыш схемы — в архитектуре (общий кластер вместо запаса на каждом сервере, масштабирование вычислений и хранения по отдельности), а не в языке. Что снижает CPU, по убыванию эффекта:

| Мера | Ожидаемый эффект |
|---|---|
| Узнать профиль команд реальных клиентов | задаёт горячий путь, без него оптимизация вслепую |
| SELECT, STATUS, UNSEEN из памяти сессии или ETS, без актора и БД | основной выигрыш; `UID SEARCH UID n:*` так уже подешевел до уровня NOOP |
| Одна запись в сокет на ответ, telemetry по выборке, `:socket` вместо `gen_tcp`, настройка `hibernate_after` | проценты, мерить |
| IDLE вместо опроса, ограничение слишком частого опроса | зависит от клиентов, потенциально кратно |
| kTLS в HAProxy | 10–30% от TLS-части, проверить поддержку |
| NIF для разбора IMAP | 5–10% от команд, плюс риск уронить ноду — не делать |
| Нативный IMAP целиком (свой на Rust или Stalwart) | уровень Dovecot, но без преимуществ BEAM |

## Схема

**Directory** (`priv/repo/migrations/*_create_directory.exs`): `tenants` (с полем `shard`), `domains`, `accounts` (`kind`: mailbox / master_inbox), `forwardings` (copy / redirect, `only_classes`, чтобы warmup не попадал в мастер-инбокс).

**Шард** (`*_create_mail.exs`). Внешних ключей на directory нет: в целевой схеме это разные базы.

- `folders`: пространство UID папки (`uidvalidity`, `uidnext`, `highest_modseq`), счётчики `messages_count` / `unseen_count`. Счётчики обновляются тем же `UPDATE`, который выделяет UID, поэтому STATUS никогда не сканирует письма.
- `messages`: узкая таблица метаданных, партиционирована по `stored_at` (недели). Индексы:
  - `(folder_id, modseq)` — для CONDSTORE;
  - частичный `(folder_id, uid) WHERE NOT \Seen` — главный запрос поллеров;
  - `(tenant_id, message_id_h)` — Message-ID и треды.
- `message_bodies`: сырые байты RFC 5322, сжатые zstd на стороне приложения. Письма около 2 KB, это ниже порога TOAST, так что Postgres сам бы их не сжал. Тела вынесены в отдельную таблицу, чтобы сканирование флагов не читало их.
- `vanished`: удалённые UID для QRESYNC.

**Почему UID не задвоятся при двух акторах (netsplit):** UID выдаются атомарным `UPDATE folders ... RETURNING`, а флаги и expunge блокируют строку папки через `FOR UPDATE`. Это проверяет тест «split brain». Уникального ограничения на `(folder_id, uid)` по всем партициям нет: Postgres требует включать ключ партиции в уникальные индексы. Гарантию даёт именно выделение UID.

## Что проверяют тесты

- Одновременный старт: 20 конкурентных `ensure` дают один актор.
- 100 конкурентных append дают UID 1..100 без дыр, счётчики корректны.
- Запись мимо актора (имитация split-brain) не даёт коллизий UID.
- Подписчик получает EXISTS / FLAGS / EXPUNGE. Повторный STORE без изменений не создаёт новый MODSEQ.
- MOVE переносит байты, выдаёт новые UID и удаляет исходные письма в одной транзакции.
- Актор останавливается по idle-таймауту, но не пока есть подписчик. Вызов, который попал на остановку актора, повторяется на новом.
- Доставка: reply попадает в мастер-инбокс, warmup не попадает; redirect не сохраняет оригинал.
- Удаление недельной партиции сдвигает `retained_from_uid` и поднимает `highest_modseq`.
- IMAP-протокол: framing с синхронными литералами и LITERAL+, разбор команд, наборы номеров (включая `n:*` за последним письмом), ENVELOPE, даты.
- IMAP-сессия без сети: LOGIN, SELECT, FETCH (PEEK не меняет `\Seen`, BODY[] меняет), STORE, SEARCH, APPEND с литералом, COPY/MOVE с COPYUID, EXPUNGE с перенумерацией, read-only EXAMINE. Push: IDLE получает новое письмо сразу; чужой EXPUNGE откладывается во время FETCH и приходит после NOOP; при падении актора сессия догоняет состояние.
- Сквозной тест по TCP настоящим клиентом, Python `imaplib` (`test/imaplib/client.py`): login, list, select, append, fetch, store, search, copy, move, expunge и IDLE, пока тест доставляет письмо через `Delivery`.
- Быстрый SEARCH: по UID и номерам — ноль запросов в БД, UNSEEN — один; `EXISTS` уходит до результата поиска.
- `UidMap` сверяется со списковой моделью на 300 случайных операциях (задействованы оба представления); память растёт с дырами, а не с письмами.
- Кеш справочника: чтения без БД, изменения в обход `Directory` подхватываются опросом, смена пароля сбрасывает кеш логинов, жёстко удалённые строки исчезают при полной перезагрузке.
- Порт для HAProxy: IP клиента берётся из заголовка PROXY, соединение без заголовка закрывается.
- Telemetry: счётчики команд по статусам, снимок видит соединения и их память.
