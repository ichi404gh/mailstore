# Postgres для шардов

Рекомендуемые настройки сервера — в [`shard.conf`](shard.conf). Там же помечено, что проверено замером на стенде (`bench/README.md`, раздел «Два шарда с синхронной репликацией»), а что пока только рекомендация. Ниже — то, что требует изменений в миграциях или коде. Это ещё не сделано.

## Patroni

- `synchronous_mode: true`: коммит ждёт синхронную реплику, и переключение ничего не теряет. Проверено на стенде с `kill -9` лидера под нагрузкой.
- `failsafe_mode: true`: если etcd недоступен, но primary видит все реплики, он не снимает себя.
- `use_pg_rewind: true`.
- etcd — 3 узла в разных зонах отказа, каждый на своём диске. На стенде etcd на общем диске с Postgres отвечал медленнее TTL лидера, и Patroni снял primary. Ресурсов etcd под Patroni нужно мало (1–2 vCPU, 1–2 GB, SSD); его можно ставить на ноды mailstore отдельным процессом с зарезервированным ядром.
- Синхронная реплика — в другом ДЦ того же региона (1–2 мс на коммит); асинхронная реплика или бэкап WAL — в другом регионе.

## Настройки таблиц (займёмся позже)

- **`folders`: `fillfactor = 85` и частая автоочистка.**
  - Каждая доставка обновляет `uidnext`, `highest_modseq` и счётчики. Этих колонок нет в индексах, поэтому обновление может быть HOT (без новых записей в индексах, меньше WAL), если на странице есть место.
  - На стенде без запаса было 82% HOT-обновлений.
  - `autovacuum_vacuum_scale_factor = 0.02`: по умолчанию очистка ждёт 20% мёртвых строк, а это 430 тыс. на 2,15 млн папок.
- **Партиции `message_bodies`: без автоочистки по вставкам.**
  - Таблица только дописывается, index-only scans по ней не нужны, но каждые 20% прироста автоочистка читает её целиком. На стенде это было видно во время замеров; главной причиной падения скорости с ростом данных это не доказано.
  - Новым партициям ставить `autovacuum_vacuum_insert_threshold = -1`, закрытую неделю один раз `VACUUM FREEZE`: дальше она неизменна, как и предполагает холодный слой.
  - Партиции `messages` не трогать: карта видимости нужна для index-only scans по `(folder_id, uid)`.
- **`message_bodies.data` уже `STORAGE EXTERNAL`** (миграция шарда): тела сжаты zstd в приложении, Postgres не сжимает их второй раз.

## Обслуживание партиций

- **Удаление по сроку** уже идёт через `DETACH PARTITION … CONCURRENTLY` с `lock_timeout`, потом `DROP` отцепленной таблицы (`Mailbox.Partitions`), трафик не блокируется.
- **Создание партиций заранее** — тоже с `lock_timeout`.

## Открытый вопрос схемы: партиции при долгом хранении

Тела и метаданные читаются по `(folder_id, uid)` без `stored_at`, поэтому Postgres не может отбросить партиции и проверяет индекс каждой. При политиках по умолчанию (год и месяц, по неделям, плюс несколько недель вперёд) это около 65 партиций, и каждый FETCH обходит их индексы.

UID папки растут вместе со временем записи, поэтому по UID можно найти неделю: хранить первый UID недели для папки (или для партиции) и добавлять в запрос условие по `stored_at`. Сначала замерить на наполненной базе.

## ОС

- XFS или ext4 с `noatime`.
- `vm.swappiness = 1`.
- Прозрачные huge pages — `madvise` или `never`; под `shared_buffers` выделить обычные huge pages.
- `vm.dirty_background_bytes` около 256 MB, чтобы ядро не копило гигабайты грязных страниц и не сбрасывало их разом.
